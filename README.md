# AtlasOps

AtlasOps is a standalone Avalonia operations workspace. It combines schema-driven domain generation, Roslyn-generated serializers and editor viewmodels, and local or Turso/libSQL persistence.

## Functional workspace

The desktop app provides:

- a unified browser for all 20 generated entity sets;
- full-text filtering within the selected entity type;
- create and delete workflows for every generated model;
- generated property editors with type validation and dirty-state tracking;
- project, connection, task, document, activity, and model-catalog dashboards;
- audit activity generated by create, delete, and save operations;
- atomic local persistence and remote Turso/libSQL replacement semantics;
- reusable navigation and document regions embedded in the desktop shell;
- routed shell commands, typed notifications, persisted settings, and layout state;
- 1,200 operational capability slices delivered across 1,110 generated implementation waves;
- 1,200 specialized Avalonia capability views with matching viewmodels, state policies, validators, repositories, services, commands, and events;
- an interactive capability studio for browsing and exercising every wave;
- a versioned world-geography catalog with 249 countries, more than 4,000
  administrative divisions, provenance, validation, indexed search, and
  persisted operator overrides;
- five reference-intelligence workbenches covering 13,463 IANA service
  assignments, 103,503 software versions, 766 CLDR locales, 99,306 regional
  cloud offers, and 94,730 Natural Earth features;
- five handwritten enterprise studios for workflow planning, policy simulation,
  incident command, inventory reconciliation, and operational reporting;
- package-backed integrations for SQLite, five external database/search
  providers, AWS, Azure, Google Cloud, JWT and credential security, seven
  interchange formats, scheduling, telemetry, and operational UI components;
- an enterprise connector runtime with typed registration, throttling, retries,
  health monitoring, optimistic checkpoints, redacted auditing, and offline
  reference connectors;
- package-backed HTTP, collaboration, AI client, data, security, document, and
  observability services with a searchable Avalonia connector workbench;
- a headless validation mode and a timed desktop startup smoke mode;
- exactly 154 solution projects, including 18 domain triplets, 14 platform assemblies, 10 adapters, 6 tools, 15 test assemblies, 3 enterprise production assemblies, 9 connector production assemblies, 28 integration assemblies, 3 operations assemblies, 4 product assemblies, and 2 extension assemblies;
- 540 modular business capabilities with validation, transition policy, optimistic repositories, approvals, service levels, dependency analysis, forecasting, reconciliation, and scenario simulation;
- 18 directly composed Avalonia domain workbenches available in the Domain modules shell tab.

## World geography reference data

AtlasOps vendors the MIT-licensed
[`countries/countries-data-json`](https://github.com/countries/countries-data-json)
dataset at the commit recorded in
`src\AtlasOps.Geography\Data\Source\SOURCE_COMMIT`. Source records remain
immutable. Country edits are persisted as a schema-versioned local overlay in
the user's application-data directory and can be reset without changing the
vendored dataset.

The geography module computes a deterministic SHA-256 fingerprint, rejects
duplicate or orphaned records, validates coordinate ranges, and builds a
trigram search index over names, aliases, country and subdivision codes,
currencies, and calling codes.

Every pack contains a `manifest.json` with source URLs, version, retrieval

Refresh all packs or one selected pack with:

```powershell
.\scripts\Update-AtlasOps-ReferenceData.ps1 -Pack All

```

The updater accepts HTTPS sources only, stages downloads in a temporary
directory, normalizes the large provider catalogs, emits deterministic
content hashes, and atomically replaces each completed pack.

The PowerShell generator emits 20 domain entities across workspace, connection, infrastructure, operations, planning, editor, observability, governance, and organization categories. The Roslyn generator consumes those annotated entities and emits:

## NativeAOT

AtlasOps is trimming and NativeAOT safe. Every production project sets
`IsAotCompatible`, and the desktop app publishes with `PublishAot`, treating
any trim or AOT analysis warning as a publish error:

```powershell
dotnet publish .\src\AtlasOps.App\AtlasOps.App.csproj -c Release -r win-x64
```

Add `-p:AtlasOpsAotRootAll=true` to root every AtlasOps assembly, so the AOT
compiler also analyzes first-party code that the desktop entry point does not
reach. The `AtlasOps NativeAOT verification` workflow runs that publish and the
native headless validation on every change.

The codebase keeps to these rules:

- JSON uses System.Text.Json source generation (`JsonSerializerContext`); the
  generated-model serializer dispatches to `AtlasOpsJsonContext`, which
  `scripts\Generate-AtlasOps.ps1` emits alongside the models.
- Interchange formats are written through explicit APIs: `MessagePackWriter`,
  Google.Protobuf `CodedOutputStream`, the YamlDotNet event emitter, an RFC 4180
  CSV writer, and Scriban `ScriptObject` models. Output is byte-identical to the
  previous reflection-based serializers.
- Connector persistence uses parameterized `Microsoft.Data.Sqlite` commands,
  JSON schema validation uses JsonSchema.Net, iCalendar output uses an RFC 5545
  writer, and Serilog events are bound from typed scalar values.
- Avalonia views use compiled bindings, and developer tools are Debug-only.

## Turso persistence

AtlasOps uses local JSON persistence by default. Set both variables to use the Turso/libSQL HTTP pipeline:

```powershell
$env:TURSO_DATABASE_URL = 'libsql://your-database.turso.io'
$env:TURSO_AUTH_TOKEN = 'your-token'
dotnet run --project .\src\AtlasOps.App\AtlasOps.App.csproj
```

The remote provider creates an `atlasops_entities` table and uses parameterized libSQL statements for loading and replacing generated entity sets. It does not silently fall back to local storage when a configured remote operation fails.

## Production operations platform

AtlasOps includes a durable operations runtime with optimistic revisions,
fencing leases, resumable checkpoints, idempotent inbox/outbox processing,
bounded retries, dead-letter recovery, and deterministic recovery planning.
Twelve provider-neutral integration families cover engineering, infrastructure,
communications, identity, monitoring, and service-management workflows. The
desktop application exposes these capabilities through five searchable
operations workbenches.

Extension manifests, ordered configuration migrations, localization fallback,
settings migration, release-channel selection, and redacted support bundles
provide product-lifecycle behavior beyond the generated model catalog.

Run `scripts\Measure-AtlasOpsComplexity.ps1` to refresh the JSON and Markdown
scorecards under `metrics`. The scorecard reports generated, scaffolded, and
handwritten source separately and exits nonzero when project, handwritten-line,
or test thresholds are not met.
